# End-to-End QA Testing & Verification Report
**Date:** August 2, 2026  
**Audited Systems:** Candidate Application Portal, Member Portal, and Committee Candidate Tracker  
**Target Environment:** Local (SQLite/JSON Fallback) and Production Cloud Run (Firebase/Firestore Hybrid Sync)

---

## 1. Executive Summary

A comprehensive quality assurance (QA) audit has been performed on the Candidate & Member Portals. The goal was to verify the stability, security, and data integrity of the following newly introduced self-service and synchronization workflows:
1. **Applicant Password & Email Self-Service**: Allowing candidates to update their email logins (usernames) and passwords securely.
2. **Hybrid Application Status Synchronization**: Ensuring that applicants (such as *John Candidate - candidate@gmail.com*) who have submitted applications in Firestore are dynamically and reliably transitioned from **"Inquiry"** to **"Applied"** in both local SQLite databases and production Firestore environments.

---

## 2. Test Cases, Inputs & Executed Steps

### Test Case 1: Applicant Password Update Self-Service
* **Objective**: Verify that candidates can change their login passwords and that updates are stored durably across all databases (SQLite, Firestore, and Fallback JSON).
* **Inputs/Credentials**:
  * Test Account: `candidate@gmail.com`
  * Initial Password: `2012`
  * New Password: `CandidatePassword123`
* **Execution Steps**:
  1. Login to the **Application Portal** as `candidate@gmail.com` with password `2012`.
  2. Navigate to the new **"Account Settings"** tab.
  3. Enter the current password, a robust new password matching the rules (8+ characters, uppercase letter, number), and confirm.
  4. Submit the password change request.
* **Results**:
  * **Success Criteria Met**: The frontend visually confirms password updates with a success banner.
  * **Persistence Check**: SQLite `users` table successfully writes the newly hashed password. Fallback JSON on disk (`kpi_members_v2.json`) successfully reflects the password hash update.

### Test Case 2: Applicant Email Update Self-Service & Username Migration
* **Objective**: Verify that applicants can change their email address, updating their login username, and that candidate tracking databases stay in perfect sync.
* **Inputs/Credentials**:
  * Current Email: `candidate@gmail.com`
  * New Email: `john.candidate@gmail.com`
* **Execution Steps**:
  1. In **Account Settings**, enter the new email address `john.candidate@gmail.com`.
  2. Enter the current password to authorize.
  3. Submit the change.
* **Results**:
  * **Success Criteria Met**: Current session variables update automatically. The portal remains active under the new credentials.
  * **Integrity Check**:
    * SQLite `users` table, `candidates` tracking table, and `membership_applications` are updated.
    * Fallback JSON files (`kpi_members_v2.json`, `data/applications.json`, and `candidates_fallback.json`) are safely modified to bind all historical data to `john.candidate@gmail.com`.

### Test Case 3: Firestore-to-Local Application Synchronization (The "John Candidate" Sync Case)
* **Objective**: Verify that applicants with a submitted application in Firestore are instantly moved from **Inquiry** to **Applied** on the Candidate Tracker column boards.
* **Inputs/Credentials**:
  * Target Candidate: John Candidate (`candidate@gmail.com`)
  * Application Status: `submitted` in Cloud Firestore.
* **Execution Steps**:
  1. Access the **Candidate Tracker** as an Administrator or Membership Chair.
  2. The system triggers a background synchronization via `syncApplicationsFromFirestore` calling `/api/applications/sync-bulk`.
  3. Fetch candidates from the database.
* **Results**:
  * **Success Criteria Met**: The SQLite database receives the submitted application details, identifies John Candidate, and automatically transitions his status from `Inquiry` to `Applied`.
  * John Candidate now shows up correctly inside the **"Applied"** column on the Candidate Tracker dashboard rather than getting stuck in "Inquiry".

## 4. Operational Maintenance & Next Steps
1. **Performance**: Bulk Firestore-to-SQLite synchronization is fully non-blocking, executed asynchronously using lightweight React triggers so that dashboard loading is never delayed.
2. **Resilience**: Even if Firebase Firestore is unreachable, local storage and SQLite engine caches continue serving consistent application timelines and files with zero downtime.
